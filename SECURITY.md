# KAYVRA Security Policy

KAYVRA takes the security of its projects and the responsible handling of vulnerability reports seriously.

## Reporting a Vulnerability

**Do not disclose suspected vulnerabilities in public Issues, Pull Requests, discussions, or social posts.**

Where a repository provides GitHub's private vulnerability reporting feature, use the **Security** tab and select **Report a vulnerability**.

If private vulnerability reporting is not available, contact the relevant repository maintainers privately through an established, verified KAYVRA communication channel. Do not send sensitive details through a public channel.

Please do not assume that a report has been received until you receive an acknowledgement.

## What to Include

A useful report may include:
- The affected repository and version, release, or commit.
- A concise description of the suspected vulnerability.
- Potential impact and realistic attack prerequisites.
- Minimal reproduction steps or a proof of concept that does not access, modify, or expose real data.
- Relevant sanitized logs, screenshots, or request examples.
- Your preferred contact details for follow-up.

Please do not attach passwords, access tokens, private keys, personal information, client data, production logs, or forensic evidence.

## Responsible Testing

- Test only systems and environments for which you have explicit authorization.
- Do not access, modify, delete, or exfiltrate data belonging to others.
- Do not perform denial-of-service testing, social engineering, or destructive testing.
- Stop testing if you encounter data that is not yours or outside the agreed scope.
- Use synthetic data and isolated test environments wherever possible.

## Coordinated Disclosure

Please allow the maintainers a reasonable opportunity to assess and address a report before public disclosure. Coordinate any proposed disclosure with the affected project maintainers.

KAYVRA does not promise a reward, fixed response time, or legal safe harbor through this policy. Any engagement-specific authorization or testing terms must be agreed separately and in writing.

## Repository-Specific Policies

If an individual repository publishes a more specific security policy, follow that policy for the affected project.
